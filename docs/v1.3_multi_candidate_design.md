# LogAnalysisSkill v1.3.0 Multi-candidate Patch Context Design

Status: frozen decision draft for review.

Trigger: real-world analyzer output exposed multiple independent terminal source
diagnostics in one build log. `root_cause_candidates` contained several
`is_terminal=true` candidates such as `E009`, `E015`, and `E020`, but
patch-suggest only prepared context for `primary_error`. The outer assistant then
patched only one diagnostic while other independent failures remained.

Goal: preserve existing single-diagnostic and large-scale cluster behavior while
adding a third patch-suggest mode for multiple independent source diagnostics.
Each independent terminal source candidate gets its own context and candidate
patch path. Cascade children remain excluded.

Non-goal: do not parse raw logs in patch-suggest. The skill may only act on
diagnostics exposed by analyzer evidence.

---

## Analyzer Additive Prerequisite

### D-A1. Add structured event fields to root_cause_candidates

Analyzer must add the following optional fields to every
`root_cause_candidates[*]` entry, copied from the corresponding scan event:

- `file`
- `line`
- `column`
- `message`
- `line_no`
- `tool`

Existing candidate fields remain unchanged:

- `rank`
- `event_id`
- `kind`
- `semantic_class`
- `confidence`
- `confidence_band`
- `confidence_reason`
- `is_terminal`
- `summary`
- `severity`

This is an additive `evidence_packet/v1` schema extension. Existing consumers
that ignore unknown fields continue to work.

Rationale: patch-suggest must not parse `summary` to recover file, line, or
message. Summary parsing is fragile and would make multi-candidate behavior
dependent on human-facing text formatting.

### D-A2. Token impact must be measured and bounded

Adding structured fields multiplies candidate payload size by the number of
ranked candidates. The implementation PR must measure token impact on real or
representative packets, including the known case where the packet used roughly
`1673 / 1800` tokens before this extension.

If candidate messages risk exceeding the 1800-token budget, the implementation
must keep the schema additive but bound text size, for example by using the
existing event `message` when short and truncating long messages with an explicit
marker. The exact truncation rule must be visible in tests if needed.

### D-A3. Existing downstream behavior remains unchanged

Single diagnostic mode, cluster mode, analyzer ranking, primary selection,
verdict gating, and workflow behavior must not depend on the new candidate
fields. They are exposed for future consumers, especially patch-suggest
multi-candidate mode.

## Patch-suggest Multi-candidate Mode

### D-B1. CLI early-dispatch priority

`run_patch_suggest` keeps early dispatch and uses this priority:

1. Load evidence.
2. If a large-scale source cluster is available, run existing cluster mode and
   return.
3. Else, if there are at least two terminal source candidates with structured
   location fields, run multi-candidate mode and return.
4. Else, run existing single diagnostic mode.

This keeps cluster mode unchanged and prevents multi-candidate logic from being
inserted into the existing single diagnostic flow.

### D-B2. Multi-candidate trigger

A candidate is eligible for multi-candidate mode only when all conditions hold:

- `is_terminal == true`
- `kind in {"compiler", "werror"}`
- structured `file`, `line`, and `message` fields are present and usable
  (`file` and `message` are non-empty strings, `line` is a positive integer)

Multi-candidate mode triggers only when at least two eligible candidates exist.
If there is only one eligible candidate, patch-suggest falls back to existing
single diagnostic behavior.

### D-B3. Cascades and non-source candidates are skipped

Candidates with `is_terminal=false` are cascade children and are not processed.
The design assumes fixing the independent terminal diagnostic may cause cascade
children to disappear.

Non-source candidates such as depsolve, linker, patch, rpm-phase, or spec-script
diagnostics are not processed by patch-suggest multi-candidate mode. The
multi-candidate overview may list them as skipped/not-applicable for user
awareness, but it must not generate patch contexts for them.

### D-B4. Output organization

Multi-candidate mode writes a top-level overview plus one context per eligible
candidate:

```text
.gbs_patch_suggest/
├── README.md
├── context.md
├── meta.json
└── candidate_context/
    ├── C001_E009/
    │   ├── context.md
    │   └── edit_specs/
    ├── C002_E015/
    │   ├── context.md
    │   └── edit_specs/
    └── C003_E020/
        ├── context.md
        └── edit_specs/
```

Each eligible candidate reuses PS-M2 source resolution:

- Level A: source context available; generate an edit-spec skeleton with exact
  whole-line `old` and `<FILL_REPLACEMENT_LINE>` for `new`.
- Level B: file/line exists but source is unavailable or ambiguous; write an
  advisory context.
- Level C: no usable file/line; this should be rare because D-B2 requires
  structured fields, but the renderer must still degrade safely if data becomes
  unusable.

Each candidate recommends one patch name:

```text
candidate_C001_E009_<basename>.patch
```

### D-B5. Token and reading behavior

The top-level `context.md` lists eligible candidates, skipped candidates, and the
recommended processing order. It must instruct the outer assistant to process
one candidate context at a time.

The overview must explicitly say:

- do not load every candidate context at once;
- do not read the raw build log;
- open one `candidate_context/<id>/context.md`, fill its skeleton if present,
  run `format-patch`, then move to the next candidate.

This mirrors cluster mode's per-file token control but changes the unit from
file to candidate.

### D-B6. Reuse existing source-diagnostic components

Multi-candidate mode should reuse:

- `CompileErrorEvidence`
- `SOURCE_DIAGNOSTIC_KINDS`
- `resolve_context`
- formatter edit-spec schema
- existing skeleton semantics where possible

It should add focused modules such as:

- `multi_candidate_ingest.py`
- `multi_candidate_render.py`

It should not hard-reuse `cluster_resolver` because cluster mode groups many
locations per file, while multi-candidate mode processes independent candidates.

### D-B7. Regression boundaries

The following behavior must remain unchanged:

- one eligible source candidate: existing single diagnostic flow;
- large-scale cluster present: existing cluster mode;
- no eligible source candidates: existing single/not-applicable behavior;
- formatter schema and behavior;
- werror support;
- "do not read raw log" guidance;
- "do not apply" invariant.

## Implementation Phasing

### PR-A: Analyzer additive fields

Scope:

- add structured fields to `root_cause_candidates`;
- measure token impact;
- verify primary/ranking/verdict unchanged;
- patch-suggest and workflow unchanged.

### PR-B: Patch-suggest multi-candidate mode

Scope:

- ingest eligible terminal source candidates from the enriched evidence;
- add early dispatch after cluster mode and before single diagnostic mode;
- write candidate overview, per-candidate context, meta, and skeletons;
- keep single and cluster modes unchanged.

---

## Invariants

- Patch-suggest does not read raw logs for multi-candidate mode.
- Patch-suggest does not call an LLM.
- Patch-suggest does not apply patches or modify source files.
- Cascade children are not treated as independent patch targets.
- Analyzer additions are schema-compatible and do not alter ranking or verdicts.
