## 二、按附录 J 改过的正文

### R-1【重要】候选同步点只取两个时刻；真正的同步时刻落在这两个时刻之外时，“版本确定”的结论不成立

- **位置**：§6.1 第 1a 条（[hld-v0.8:458-459](docs/enhance/vd-cosmos-loganalyzer-hld-v0.8.md#L458-L459)）、§14 第 14 条。
- **依据**：p4 的版本号只增不减。所以一个文件在两个时刻的版本号相同，只能说明这两个时刻**之间**没有提交，说明不了区间之外的情况。
- **反例一（同步晚于开始时间）**：
  - shelve 包 P 的 SCL 是 10-16 创建的；本轮 10-22 13:26 开始；另一位同事在 13:40 提交了 `foo.c#6`；
  - Cosmos 在 14:05 编译 P 时才同步，实际编的是 #6；
  - 两个候选时刻 @SCL 和 @13:26 都得到 #5，于是记成“版本确定 #5”；
  - 如果错误行在 #5 和 #6 里相同，源码行核对也会通过。
- **反例二（base 早于 SCL）**：§14 第 14 条自己就列了“另有 base 清单”这种可能。如果清单钉在比 SCL 更早的 CL 上（例如 product 快照 10-01），区间同样没有覆盖。
- **后果**：取错了版本，却被标成“确定”。这正是上一轮 R-2 想解决的问题。

```diff
-     - **候选同步点**：`路径/...@SCL`（该 CL 号所处时刻）和 `路径/...@<报告 Start Time>`……
+     - **候选区间**：下端取所有可能同步点中最早的一个（@SCL；有 base 清单或快照 CL 时取其中更早者），
+       上端取"该包编译结束之前"的最晚时刻（该包失败日志响应的 Last-Modified，已在 §5.4 第 1 条的留证里；拿不到时用报告首次出现该包失败的观察时间）。
+     - 两端版本号相同 → 版本确定（区间内没有提交）；否则版本不确定。下端无法覆盖 base 清单时，记"下端未覆盖 base 清单"。
-     各候选得到同一个 #rev → 记"版本确定"（与第 14 条的答案无关）
+     第 14 条的答案只要落在区间内，就不影响结论
 §14 第 14 条 ① 增加：Cosmos 是在 Start Time 一次性同步，还是在各包开始编译时才同步。
```

- **副作用**：上端往后推，版本不确定的文件会多一些，仅诊断的比例会上升，但结论是诚实的。用日志的 Last-Modified 作上端，比用“首次观察到的时间”紧得多：19091860 是隔了 4 天才观察的。
- **夹具**：假 p4。`foo.c` 在 @SCL 和 @Start 都是 #5，在日志的 Last-Modified 时刻是 #6 → 期望“版本不确定”、仅诊断。

### R-2【重要】人工终态的窗口按“同上”的规则，会被详情页再次显示“运行”作废；而“运行中但报告稳定”正是需要人工终态的场景

- **位置**：[hld-v0.8:369-370](docs/enhance/vd-cosmos-loganalyzer-hld-v0.8.md#L369-L370)（“窗口要求同上”）；[§8.1 第 1 条](docs/enhance/vd-cosmos-loganalyzer-hld-v0.8.md#L656)；§9.5 第 4 条。
- **问题**：可信终态那一条写了“之后再次观察到运行 / 排队，或可信来源失效 → 窗口作废”。人工终态写的是“窗口要求同上”，按字面会连这条作废规则一起继承。
- **反例**：
  - 详情页（身份为强）一直显示 running；12:00 写出 `running_but_stable`；
  - 12:05 FatTank 执行 `confirm-terminal`；
  - 12:06 观察时详情页仍显示 running → 窗口作废；之后每一轮都作废，永远不会定型。
  - 详情页一直抓取失败时，结果也一样。
- **后果**：上一轮 R-1 的修复实际上不起作用，loop 照样无声地等下去。
- **另一个含义不清的地方**：§8.1 写的是“**没有**可信来源时，FatTank 执行 confirm-terminal”。可信来源明确说“运行中”的时候，这条人工确认能不能满足起轮闸门，没有写。

```diff
-     - **人工终态**：……以确认时间作为 terminal_epoch，窗口要求同上；不改写 execution_state。
+     - **人工终态**：……窗口 = [max(连续相同记录起点, 确认时间), 最近一次观察时间]，至少两次成功观察、长度 ≥ `poll.interval_s`。
+       只因报告摘要变化而作废（confirm-terminal 本来就绑定报告摘要）；详情页再说"运行 / 排队"或详情抓取失败都不作废，
+       两者冲突写进证据和报告。
 §8.1 第 1 条：
+   可信来源明确说"运行 / 排队"时，confirm-terminal 只用于定型，不满足起轮闸门；
+   要用于闸门，命令必须带 `--override-running`，回显详情页的状态与观察时间，并留痕。
```

- **副作用**：“定型”与“闸门”在人工终态上的作用分开了，§9.5 第 4 条要同步修改。
- **夹具**：
  - `status_seq/running_forever_stable/`：执行 confirm-terminal 后，详情页仍是 running → 期望过一个间隔后定型，依据为 `manual_terminal`；
  - 不带 `--override-running` 时，期望闸门不通过。

### R-3【重要】“压缩包加补丁”按 spec 的 Source 判断，会把几乎所有按 GBS 惯例打包的包都判成“源码在压缩包内”

- **位置**：[hld-v0.8:456](docs/enhance/vd-cosmos-loganalyzer-hld-v0.8.md#L456)。
- **问题**：按 Tizen / GBS 的惯例，spec 几乎都写 `Source0: %{name}-%{version}.tar.gz`；压缩包是构建时从源码树现打出来的，depot 里放的是展开的源码。
  - 样本日志里的 `BUILD/AT-HUB-1.8/` 这类目录名，就是这样生成的；
  - 仓库自己的 spec 夹具也全部写了 `Source0: *.tar.gz`；
  - VD 的 spec 是否也是这样，请在构建机上看一眼 7 个样本包的 spec。
- **后果**：按字面实现，7 个样本包全部变成仅诊断，第 3a 批的准确性验收没法进行。
- **改法**：

```diff
-   - （v0.8）**包根里是上游压缩包加补丁**（spec 的 Source 是 `*.tar.*` / `*.zip`，开源库常见）：……
+   - （v0.8）**包根里是上游压缩包加补丁**：判据是"主错误文件按第 ① 类换算后不存在"，并且"包根里确实有 spec 的 Source 指向的压缩包文件"
+     （`p4 files <包根>/...<Source 文件名>` 存在）。spec 写了 Source 压缩包、但包根里是展开的源码树（GBS 构建时现打包）→ 照常按第 ① 类处理。
```

- **夹具**：
  - spec 写 `Source0: %{name}-%{version}.tar.gz`、depot 里是源码树 → 期望按 ① 正常定位；
  - depot 里有 `foo-1.2.tar.gz` 加 `*.patch` → 期望“源码在压缩包内”。

### G-1【一般】快照核对里“无法核对”与“不一致”的区分没有可执行的规则

- **位置**：[hld-v0.8:466](docs/enhance/vd-cosmos-loganalyzer-hld-v0.8.md#L466)：“无法确定显示规则的差异记无法核对”。
- **问题**：工具拿到的只是两行字符串不相等，无从知道差异是否来自显示规则。实现方只能全部判成“不一致”（变成仅诊断），或者全部判成“无法核对”（不降级），两种做法的后果相反。另外，主错误文件“无法核对”时要不要降级，§6.1 列的仅诊断原因里也没有写。
- **改法**：
  - 判“无法核对”的条件：规范化之后仍不相等，而所有差异都只落在日志一侧的 `<XX>` / `<U+XXXX>` 标记里，或者快照一侧的非 ASCII 字节里。其余差异一律判“不一致”。
  - 主错误文件“无法核对”时不降级，但要在任务包里醒目标注。
- **夹具**：
  - 含 EUC-KR 注释的行，差异只在注释里 → 无法核对；
  - 同一行里另有 ASCII 差异 → 不一致。

### G-2【一般】②' 类路径的“本包目录名”不能靠报告里的包名去拼

- **位置**：[hld-v0.8:453](docs/enhance/vd-cosmos-loganalyzer-hld-v0.8.md#L453)。
- **问题**：BUILDROOT 的目录名来自 spec 的 Name / Version / Release。报告里的包名可能与 spec 的 Name 不同，比如大小写不同（`AT-HUB` 对 `at-hub`）；release 号工具也不知道。
- **后果**：拼不出本包目录名，于是被归入 ② 类，误判成“转交其他包”，和这一类想解决的问题正好相反。
- **改法**：本包的 BUILDROOT 路径从日志里取，例如 `RPM_BUILD_ROOT=` 或 `+ cd …/BUILDROOT/…` 这类行；取不到时，再按“报告包名 + 忽略大小写的前缀”匹配，并标注“推断”。
- **夹具**：spec 的 Name 与报告包名大小写不同，期望仍然归入 ②'。

### G-3【一般】“属于清单某个族的新子标志按族处理”，在禁止前缀匹配的前提下执行不了

- **位置**：[hld-v0.8:507](docs/enhance/vd-cosmos-loganalyzer-hld-v0.8.md#L507)。
- **问题**：要判断一个清单里没有的标志属于哪个族，只能拿新版本 Clang 重新生成族的展开结果，或者按前缀猜，而前缀匹配是明令禁止的。
- **反例**：Clang 升级后出现了 `-Wformat-<新名字>`。新版本的族展开还没生成，工具无法判断它属于 `-Wformat` 族，于是按“不在清单里”处理，漏过强制人工定性。
- **改法**：每轮记录 Cosmos 用的 Clang 版本，与清单生成时的版本比较。版本不同时写待办；在重新生成之前，名字以强制档某个族名为前缀的未知标志，临时按强制档处理。前缀只能用来把标志往强制档提，不能用来往下降档。
- **夹具**：清单的版本与本轮 Clang 版本不同，出现一个前缀为 `-Wformat-` 的未知标志 → 期望强制人工定性，并写待办。

### G-4【一般】防泄漏的机械检查：第 3a 批要检查的那一段是空的；样本名也没有考虑别名

- **位置**：[hld-v0.8:964](docs/enhance/vd-cosmos-loganalyzer-hld-v0.8.md#L964)。
- **问题一：检查范围**。第 3a 批不带案例检索，任务包里的知识库上下文段是空的，只搜这一段等于没有检查。第 3a 批真正可能泄漏的地方，是知道答案的人写出来的那些内容：团队规则、本线的分析模板、SKILL.md、patch-suggest 的 context。
- **问题二：别名**。名字的写法不止一种：
  - README 里用的就是简写（`aria-engine`、`picture-test`）；
  - 日志里的 BUILD 目录名带版本号（`com.samsung.tv.aria-engine-3.005.05`）。
  - 只按报告里的全名搜索，以后有页面写简写时就会漏掉。
- **改法**：
  - 检查范围改为“任务包里除本包证据段和源码段以外的全部内容”（规则、模板、skill、patch-suggest context、知识库上下文）；
  - 样本名清单按包列出所有别名：报告全名、BUILD 目录名、spec Name、depot 路径的最后一级、文档里出现过的简写。这份清单和参照集一起冻结。
- **夹具**：分析模板的示例里写了 `AT-HUB` → 期望 FAIL；某个案例页正文写了 `aria-engine`（简写）→ 期望被排除。

### G-5【一般】用空票据文件模拟“未登录”时，待办给出的登录命令会把真实票据写进验收用的文件

- **位置**：[hld-v0.8:954](docs/enhance/vd-cosmos-loganalyzer-hld-v0.8.md#L954)；§3 第 6 条“`p4.tickets_file` 不是默认路径时，命令前加 `P4TICKETS=<该路径>`”。
- **问题**：在验收的覆盖模式下，待办会给出 `P4TICKETS=<空文件> p4 … login`。FatTank 照着执行“登录后自动继续”这一步，就会在验收目录里留下一张有效的票据。
- **改法**：
  - “登录后继续”这一步改为撤掉覆盖、回到默认票据文件，不需要重新登录；
  - 覆盖模式下，待办正文注明“验收模拟，不要执行登录”；
  - 空票据文件放在 `verification/<run_id>/` 的输出范围之外，权限设为 0600，验收结束时由脚本核对它为空并删除。
- **夹具**：验收结束后，期望票据文件不存在，或大小为 0。

### G-6【一般】金丝雀“记录目录摘要”会读到凭据类 skill 的内容

- **位置**：[hld-v0.8:531](docs/enhance/vd-cosmos-loganalyzer-hld-v0.8.md#L531)。
- **问题**：用户平时的 `.cline/skills` 里有凭据类 skill。对整个目录的内容算摘要，就要逐个读这些文件，与 §3 第 6 条“工具从不读取……”相冲突。
- **改法**：目录摘要只基于文件清单（名字、大小、修改时间）计算；只读取金丝雀 skill 本身的内容来核对标记。

### G-7【一般】只有“不计数的跳过”时，可能还没有 contention_id，`loop_starved` 就没有依据版本

- **位置**：[hld-v0.8:833](docs/enhance/vd-cosmos-loganalyzer-hld-v0.8.md#L833)，以及下面 contention_id 那一条。
- **问题**：30 分钟里全是人工事件或本构建事件引起的跳过时，有没有生成 contention_id，文字没有写清楚。
- **改法**：写明“任何一次跳过（计数或不计数）都开始一段争用，并生成 contention_id”。
- **夹具**：30 分钟内全是不计数的跳过 → 期望写 1 条 `loop_starved`，依据版本不为空。

**N4｜重要｜P4 结果分类要求的字段并非两种输出方式都保证提供，且不能完全忽略进程状态**

**位置：**§3 第 6 条，第 212—215 行。

**触发与后果：**文档把 `-ztag -s` 与 `-G` 当成等价的数值错误分类接口，并写“不看退出码”。但 `-s` 本身只是给输出增加 `info:`、`error:` 等前缀，不保证提供足以区分各类原因的数值错误码；进程异常终止还可能根本没有完整错误记录。[Perforce 全局选项说明](https://help.perforce.com/helix-core/server-apps/cmdref/current/Content/CmdRef/global.options.html)

**反例：**`print` 已输出部分内容，随后进程被杀，没有结构化错误尾部。若忽略进程状态，不能仅凭已收到的数据判定文件读取成功；空或残缺的 `describe` 输出也不能证明 shelf 已删除。

候选修改：

```diff
- 一律用 -ztag -s（或 -G）……不看退出码。
+ 固定使用经构建机版本验证的结构化输出协议，
+ 并保存该版本各错误类别的录制夹具。
+ 先检查进程是否正常结束、输出是否完整且可解析；
+ 异常终止、残缺输出、缺少预期字段均算快照失败。
+ 正常结束后结合命令、结构化消息分类；
+ 退出码不能单独决定业务类别，但必须作一致性检查。
+ 无法明确分类时记 p4_unclassified，不据空输出认定历史输入已不存在。
```

**副作用：**需要固定一种适配方式；无法识别的服务端返回会保守停止，而不是误判为仅诊断。  
**夹具：**正常无匹配、无权限、未登录、已删除 shelf、混合成功和错误消息、输出中途被杀、非零退出但无错误记录。

**N6｜一般｜跨仓库补边只有 Provides，缺少“谁需要什么”的来源**

**位置：**§7.8 第 1 条，第 636—639 行；§14 第 15 条。

**触发与后果：**当 builddepinfo 没有 product→base 边时，仅查询 repodata 的 Provides 只能找到能力提供者，不能推出哪个 product 包需要该能力。正文只要求读取“本轮变动包”的 BuildRequires，未变动包的缺失边仍补不出来。

**反例：**未变动的 product 包 A 构建时需要 `pkgconfig(x)`，builddepinfo 省略跨仓库边；base 的 X 提供该能力。存在 X 并不能证明 A→X，尤其构建依赖未必出现在二进制运行依赖中。

候选修改：

```diff
- 不在文件里，就用 repodata 的 Provides 解析补上。
+ 缺失跨仓库边时，先取得消费者的需求证据：
+ 对应版本的构建依赖元数据，或 spec 中可可靠解释的 BuildRequires。
+ 再用匹配架构和快照的 Provides 解析提供者。
+ 需求来源不明或宏无法解析时标“跨仓库关系未核实”，不生成确认边。
```

**副作用：**可能需要读取部分未变动包的 spec；无法确定时保留缺口标记。  
**夹具：**上述未变动消费者；仅构建依赖无运行依赖；多个提供者；带条件宏的需求。
