## 二、一般

### G-1 完成状态失效之后，已生成的任务包和已接收的分析结果怎么处理，没有写；“已有通过校验的结果就不再要求分析”没有说按什么判断

- **位置**：§5.4 第 3 条（[hld-v0.9.2:398](docs/enhance/vd-cosmos-loganalyzer-hld-v0.9.2.md#L398)）；§9.2（[881](docs/enhance/vd-cosmos-loganalyzer-hld-v0.9.2.md#L881)）。
- **触发条件**：在“按时长完成”的那段时间里（详情页一直不可用）已经下载了日志、生成了任务，ClineSR 的结果也被接收了。之后取得可信终态（或者详情页恢复、显示运行），按 v0.9.2 的口径，当前完成状态失效、日志要重新验证或重取。重取到的日志摘要变了，比如构建后来又写入了一批错误。
- **反例**：
  - tvs-ext 在按时长完成时，日志停在 `-ferror-limit` 截断之前，生成的任务也已经分析并接收；
  - 终态窗口完成后重取日志，日志变了；
  - §9.2 写的是“已有通过校验的结果就不再要求分析”，如果按包来判断，tvs-ext 不会再分析，新一轮闸门用的就是基于旧日志的结论。
- **后果**：分析结论和最终日志对不上，没有任何标记。

```diff
 §9.2
-- 分析：每个 attempt 一个独立目录；已有通过校验的结果就不再要求分析；尝试次数有上限。
+- 分析：每个 attempt 一个独立目录；"已有通过校验的结果"按（包、任务输入摘要）判断，输入摘要包括最终日志摘要、
+  快照清单摘要和规则集版本，不按包判断；尝试次数有上限。
+- （v0.9.2 补）完成状态失效后重新取得的最终日志，摘要与生成任务时用的日志不同 → 以旧日志生成的任务包和已接收结果
+  标"输入已过期"（保留作记录，不进处置账本），按新日志重新生成任务；摘要相同（已验证没变）→ 原结果继续有效。
```

- **副作用**：同一个包可能需要重新分析一次。
- **夹具**：
  - 按时长完成 → 生成任务并接收结果 → 终态后重取日志，摘要变化 → 旧结果标“输入已过期”，生成新任务；
  - 摘要不变 → 不重新分析。

### G-2 任务包的分段清单必须覆盖整个文件、互不重叠；工具证据段只由“写过什么”来约束还不够

- **位置**：§6.1 第 4 条（[532](docs/enhance/vd-cosmos-loganalyzer-hld-v0.9.2.md#L532)）；§11 第 3 条（[1029](docs/enhance/vd-cosmos-loganalyzer-hld-v0.9.2.md#L1029)）。
- **伪造标题的绕过已经堵住了**。剩下两个缺口：
  - **段之间有空隙**：段按字节范围登记，但没有要求这些范围铺满整个文件。只要生成器有缺陷，把模板文字追加在最后一段之后，或写进两段之间的空隙，这些字节不属于任何段，也就不会被检查。
  - **证据段里混进模板文字**：证据段不受检查。如果生成器把模板文字放进了证据段，检查同样看不到。
- **改法**：

```diff
+  分段清单必须首尾相接地覆盖整个任务包文件（从 0 到文件长度，不重叠、无空隙），验收脚本先核对这一点，不满足即 FAIL；
+  分段清单本身计入登记的输入摘要。工具证据段的内容只能是：登记过的字段（构建号、包名、通知行，按固定格式），
+  以及与日志文件或快照文件逐字节对应的片段（登记来源文件和偏移，验收时按偏移比对摘要）；其它文字出现在证据段里即 FAIL。
```

- **夹具**：
  - 最后一段之后多出 10 个字节 → FAIL；
  - 证据段里有一行不对应任何日志或快照偏移的文字 → FAIL；
  - 样本自身的正常任务包 → 通过。

### G-3 “实际修法的特征串”如果取了通用写法，会在模板和规则段里误命中

- **位置**：§11 第 3 条②。
- **反例**：
  - aria-engine 的实际修法是 `__attribute__((unused))`；
  - tvs-ext 是 `using Base::SetResolution;` 这类写法；
  - 本线的 R08 骨架模板、SKILL.md 的示例里，完全可能有 `__attribute__((unused))`、`-Wno-error=` 这样的通用片段。
  - 结果是所有任务包都 FAIL，或者为了避免 FAIL 而把这一项检查放松。
- **改法**：特征串必须含有本包特有的东西（成员名 `m_moduleID`、文件路径、CL 号）。冻结参照集时，拿一个非样本包的任务包，对它的规则段、模板段、参考段跑一遍特征串，有任何命中，该特征串就作废，不能入库。
- **夹具**：
  - 特征串为 `__attribute__((unused))` → 冻结时被拒绝；
  - 特征串为 `m_moduleID` → 冻结时接受，只在样本泄漏时命中。

### G-4 分支标记的集合没有写死；真实路径里有好几个方括号段

- **位置**：§6.1 对应规则（[489](docs/enhance/vd-cosmos-loganalyzer-hld-v0.9.2.md#L489)）：“`[INT]` / `[FET]` / `[COSMOS]` 一类标记”。
- **真实写法**：仓库里保存的真实报告片段里，路径是 `//TIZEN/[MAIN]/[TIZENPROD_Prj]/[INT]/PLATFORM/…/libdeflate/...@13387272`，方括号段不止一个。
- **后果**：“一类”可以理解成“所有方括号段”。如果连 `[MAIN]` 也去掉，不同主线的路径会被配成同一个包；只去掉 `[INT]` 又会留下 `//TIZEN/[MAIN]/[TIZENPROD_Prj]//PLATFORM` 这样的双斜杠，配对结果取决于实现方怎么处理斜杠。
- **改法**：

```diff
-        包键是把路径里 `[INT]` / `[FET]` / `[COSMOS]` 一类标记去掉后的包根路径
+        包键是把路径里**整段等于**配置 `cosmos.branch_markers`（默认恰好 `[INT]`、`[FET]`、`[COSMOS]`）的路径段去掉、
+        再把连续斜杠合并后的包根路径；其它方括号段（如 `[MAIN]`、`[TIZENPROD_Prj]`）原样保留，参与配对。
```

  附录 B 增加 `cosmos.branch_markers`。

- **夹具**：
  - `[INT]` 与 `[FET]` 只差这一段 → 能配对；
  - `[MAIN]` 与 `[DEV]` 不同 → 不能配对；
  - 去掉标记后的双斜杠 → 合并后正常配对。

### G-5 跨分支 shelve 如果是常态，3 个 shelve 样本都会变成仅诊断；需要预先设一个决策点

- **位置**：§6.1 同分支与跨分支（[496-499](docs/enhance/vd-cosmos-loganalyzer-hld-v0.9.2.md#L496-L499)）；§14 第 16 条⑦。
- **问题**：真实路径带 `[INT]`、`[FET]` 这样的分支段，而附录 I 写的是“报告里 shelve 包那一行显示 shelve 所在分支的路径”。这说明 VD 线很可能经常把 shelve 放在 FET 分支、base 清单在 INT 分支。
- **后果**：如果⑦统计出多数 shelve 包都跨分支，那么：
  - AT-HUB、aria-engine、plusplayer 这 3 个样本全部只能诊断；
  - “shelve 合并”这一整套设计在第 3a 批几乎用不上；
  - 准确性验收里有 3/7 的样本会落进“输入不足”。
- **改法**：§14 第 16 条⑦增加两项：
  - 跨分支时 Cosmos 怎样应用 shelve（unshelve 带分支映射、按同一相对路径映射，还是别的）；
  - 预设判断规则：只要 3 个样本里有跨分支的，第 3a 批开工前就要定下“按 `[FET]`→`[INT]` 同一相对路径映射，再按集成记录找共同祖先”的规则（或明确接受这些样本只能诊断），并在验收结论里注明。

### G-6 shelve 动作还差两处：move 的比较对象，以及合并后关键字的重新展开

- **位置**：[509](docs/enhance/vd-cosmos-loganalyzer-hld-v0.9.2.md#L509)、[513](docs/enhance/vd-cosmos-loganalyzer-hld-v0.9.2.md#L513)。

**1. move。** 在 shelve 里，move 是 move/add（新路径）和 move/delete（旧路径）两条记录，基础版本属于旧路径。规则里“基础版本与本轮版本相同”要求同一个 depot 文件，而新路径在清单 CL 上并不存在，于是这条比较没法执行。实现方要么一律判合并失败，要么一律判原样叠加。

- 改法：两条记录配成一对处理：
  - 旧路径的基础版本等于清单 CL 上的版本，并且新路径在清单 CL 上不存在 → 原样叠加；
  - 否则 → 合并失败（移动的文件已被改过，或目标路径已存在）。

**2. 关键字重新展开。** 合并出来的文件不对应任何 depot 版本，`$Revision$`、`$DateTime$` 这类关键字“按 Cosmos 编译时的规则重新展开”时，填什么值没有定义。

- 改法：合并结果保持不展开，标“关键字未展开”。错误恰好落在关键字所在行时，快照核对记“无法核对”。

**夹具**：
- move 一对，旧路径版本相同 → 原样叠加；旧路径已被改过 → 合并失败；
- `+k` 文件合并后错误落在 `$Id$` 那一行 → 无法核对。

### G-7 `confirm-terminal` 按架构绑定，但还没发布的架构怎么写，没有说

- **位置**：§8.1（[717](docs/enhance/vd-cosmos-loganalyzer-hld-v0.9.2.md#L717)）。
- **问题**：`running_but_stable` 的条件里写的是“全部**已发布**架构”，说明确认的时候可能还有架构没有发布。这时 `--report-digests` 里该架构填什么？如果直接跳过不填，它以后发布时就不会让确认失效。
- **改法**：未发布的架构绑定“未发布”这个标记，以后发布了就算“变化”，确认失效；命令回显时把它列出来。
- **夹具**：确认时 x86_64 还是 404，之后发布 → 期望确认失效。

### G-8 §14 第 16 条⑥要读“已存下的”执行日志页和步骤页，这两类页面也可能含凭据

- **位置**：§14 第 16 条⑥（[1093](docs/enhance/vd-cosmos-loganalyzer-hld-v0.9.2.md#L1093)）。
- **问题**：同一个构建的变量页上有 `BART_PASSWD`；构建步骤如果在命令行里使用它，并开着 `set -x` 或打印了环境变量，执行日志页里就会出现它的值。变量页为此专门定了白名单、不落盘的规则，日志页和步骤页却已经整页存在磁盘上，接下来还要人去读。
- **改法**：
  - 侦察前先对这两份已保存的文件过凭据检查，命中就请 FatTank 删除后重新获取；
  - 侦察只用固定的模式抽取 3 个样本包的同步命令行（包根路径加 `@CL`），不浏览全文；
  - 以后如果由工具读取日志页来确认第 14 条①，按变量页的规则执行：不落盘，只按白名单抽取行。

**1. 重要：停顿或重启后的第一次详情失败，仍可能立即按时长定型**

位置：[§5.4 第 3 条，第 397 行](/home/toolchain/development/LogAnalysisSkill/docs/enhance/vd-cosmos-loganalyzer-hld-v0.9.2.md:397)，附录 B 第 1150 行、附录 L 第 1 条。

触发条件与后果：两次观察间隔超过 `settle_s`，期间没有观察。当前公式把这段无人观察的时间全部算成“未知持续时间”，仍然不能保证文中承诺的“一次详情抓取失败不能定型”。

反例：

- 10:00：报告摘要 H，可信状态为“运行”。
- 进程停顿，10:40 恢复；报告仍为 H，详情第一次抓取失败。
- 连续相同记录起点和最近可信观察都是 10:00，窗口为 2400 秒，立即超过默认 1800 秒。

这可能提前定型，继而把尚未发布完整的报告判成对账失败。它不会直接绕过起轮闸门，但会错误停止读取推进。

候选修改，替换 §5.4 对按时长窗口的定义，并同步附录 B、L：

```diff
- 窗口起点 = max(连续相同记录的起点, 最近一次可信状态观察的时间)
+ 可信状态之后首次实际观察到“未知”时，记录 unknown_since。
+ 窗口起点 = max(连续相同记录的起点, unknown_since)。
+ 窗口内须至少有两次报告成功、有效状态为未知的观察。
+ 再次观察到可信状态即清除 unknown_since；该字段落库并跨重启保留。
+ 未配置可信来源时，unknown_since 从首次成功观察报告时开始。
```

副作用：状态来源失效后，通常多等一个轮询间隔；长时间停机后不会凭停机时长直接定型。

测试夹具：上述“运行→停机 40 分钟→一次详情失败”；排队、终态各一组；随后未知持续满窗口应定型；重启前后计时一致。

**2. 重要：逐行核对不能证明变量页属于本构建**

位置：[§6.1 第 1a 条，第 486 行](/home/toolchain/development/LogAnalysisSkill/docs/enhance/vd-cosmos-loganalyzer-hld-v0.9.2.md:486)，附录 B 第 1145 行、附录 L 第 8 条。

触发条件与后果：变量页地址模板误指另一构建，或返回另一构建的页面；两次构建的报告输入相同，但 shelve 包请求的 base 不同。所有新增清单核对仍可通过，随后从错误 base 取源码。

反例：构建 A、B 的普通包、报告头和 `SHELVE_LIST` 完全相同，都有 `P@=300`；A 的 `PACKAGE_LIST` 为 `P@100`，B 为 `P@200`。报告中没有该 shelve 包的 base CL，因此拿 B 的变量页核对 A，无法发现 100→200 的错误。

HTTPS、不跟随重定向和清单唯一配对均不能补上这个身份缺口。

候选修改：

```diff
- 变量页的身份不另做核对：下面与报告的逐行核对就足以证明它属于本构建。
+ 清单核对只证明输入相容，不证明构建身份。
+ 地址模板必须包含唯一的 {build_id}；展开后的主机和构建路径必须匹配当前构建。
+ 变量页按固定头部规则核对自身构建号或自身链接，不从变量值中推断身份。
+ 身份缺失或不符时不自动登记清单；转 bind-base-list 人工绑定并留理由。
+ 身份检查只读取所需的头部结构，不扩大变量值白名单。
```

副作用：需侦察变量页的身份结构；没有可核验身份的实例暂时走人工退路。普通包及 shelve 清单的逐项核对仍须保留。

测试夹具：A/B 报告相同但 shelve base 不同；固定写死另一构建号的模板；正确地址返回错误构建头；身份缺失；正确身份但清单不符。前四类不得自动登记。

**3. 重要：把整个 shelve 的文件集合用于分支判定，会误伤跨包 shelve**

位置：[§6.1 第 1a 条，第 497～498 行](/home/toolchain/development/LogAnalysisSkill/docs/enhance/vd-cosmos-loganalyzer-hld-v0.9.2.md:497)，同节第 520 行、§14 第 16 条⑦、附录 L 第 2 条。

触发条件与后果：同一 SCL 修改多个包。当前“每个文件都在清单那一行包根下才算同分支”的条件，与第 520 行允许跨包 shelve、仅叠加本包文件的规则冲突。

反例：SCL 同时修改：

```text
//depot/INT/A/src/a.cc
//depot/INT/B/src/b.cc
```

分析 A，清单包根为 `//depot/INT/A`。B 的文件在 A 根外，按新规则整个情形进入“跨分支”，尽管 A 的修改完全同分支。正常可还原的样本会被降成仅诊断，侦察的跨分支计数也会偏大。

此外，真正跨分支时，必须明确“在 shelve 里”如何对应到 base 文件：`FET/A/src/a.cc` 改过，不能因为 `INT/A/src/a.cc` 的完整 depot 路径不同，就把后者当作未被 shelve 修改的“请求 base”。

候选修改：

```diff
- shelve 里每个文件……都落在清单那一行的包根之下……
+ 先按报告中的 shelve 包根划定本包文件集合；
+ 已明确属于其它包的文件只记录，不参与本包分支判定。
+ 对本包比较原样 shelve 包根与原样 base 包根，判同分支或跨分支。
+ 跨分支时，用包内相对路径标记 base 中受 shelve 影响的对应文件；
+ 此对应只用于阻止误放行，不用于跨 depot 比较 #rev 或取文件。
+ 无法唯一对应时，本包仅诊断；不得把受影响文件标为“请求 base”。
```

同步修改 §14 第 16 条⑦的统计口径。

副作用：需要保留本包文件集合及对应关系；无法映射的跨分支情况仍保守降级。不会增加跨分支自动合并能力。

测试夹具：同分支双包 SCL；真正跨分支单包 SCL；跨包和跨分支混合；相同相对路径的 base 文件必须保持来源未核实；前缀相似包根不得串包。

**4. 一般：合并工具的退出码描述不能直接用于子进程返回值**

位置：[§6.1 第 1a 条，第 514 行](/home/toolchain/development/LogAnalysisSkill/docs/enhance/vd-cosmos-loganalyzer-hld-v0.9.2.md:514)，附录 L 第 7 条。

触发条件与后果：`git merge-file` 发生普通工具错误。文档规定“大于 0 都是冲突处数”，会把工具错误显示成大量内容冲突。

反例：本次只读执行 `git merge-file -p`，给三个不存在的输入路径，实际进程退出码为 **255**。按现规则会报告“冲突 255 处”。虽然仍拒绝合并结果，但错误原因和后续人工处置会失真。Git 的冲突计数上限实际是 127。[Git 官方说明](https://git-scm.com/docs/git-merge-file)

候选修改：

```diff
- 退出码 0 = 无冲突，大于 0 = 冲突处数，小于 0 = 出错
+ 按子进程接口实际返回值分类：
+ 0 = 无冲突；1～127 = 内容冲突（127 表示达到计数上限）；
+ 128～255、信号终止、启动失败、超时 = 工具错误。
+ 除 0 外均不得接收合并结果；保留净化后的错误类别。
```

副作用：不改变放行条件，只纠正通知、报告和待办中的失败分类。

测试夹具：无冲突、一个冲突、冲突计数达到上限、输入缺失返回 255、启动失败、信号终止、超时。
