## 重要

### R-1 详情页一次抓取失败，就让“按时长定型”在构建运行期间生效

- **位置**：§5.4 第 3 条“按时长”（[hld-v0.9.1:390](docs/enhance/vd-cosmos-loganalyzer-hld-v0.9.1.md#L390)）；附录 B 的 `poll.settle_s`（[1130](docs/enhance/vd-cosmos-loganalyzer-hld-v0.9.1.md#L1130)）。
- **触发条件**：“有效执行状态为未知”被定义为“没有可信来源、**详情失败**，或身份为弱”；而“不拿以前某次的结果填补本次的未知”。所以只要有一次详情抓取失败，那一刻的状态就是“未知”，按时长的窗口又是从“连续相同记录的起点”开始算，失败之前累积的时长全部有效。
- **反例 A（运行中）**：
  - 10:00 起报告不再变化，详情页一直显示 running；
  - 10:35 详情页返回一次 500，状态记为“未知”；
  - 报告已经不变 35 分钟，超过 30 分钟，当场按 `elapsed_window` 定型；
  - 运行期间静止的半成品报告就这样被定型了，这正是 K H1 / C N2 要防的情形。
- **反例 B（刚观察到终态）**：
  - 10:40 第一次看到 failed，记下 terminal_epoch；
  - 10:41 详情页 500，按规则终态窗口作废，状态变为“未知”；
  - 记录从 10:00 开始算，已有 41 分钟，立刻定型；
  - 附录 K 第 3 条说的“不能用终态之前累积的时长代替终态之后的窗口”，被一次抓取失败绕过了。
- **后果**：详情抓取失败本来就常见（为此单独设了计数和待办），每一次都可能让未完成的报告被定型；接着拉取日志、生成通知，都基于半成品。

```diff
       - **按时长**（v0.9 收窄）：连续相同记录持续 ≥ `poll.settle_s`（默认 1800 秒），并且**有效执行状态为"未知"**……
+        按时长的窗口 = [max(连续相同记录的起点, 最近一次可信状态观察的时间), 最近一次观察时间]：
+        只有"自最近一次可信观察（运行 / 排队 / 已结束，身份为强）以来一直是未知"的时长才算数；
+        从未有过可信观察（没有配置来源、或一直是弱身份）时，才从连续相同记录的起点算起。
+        "最近一次可信状态观察的时间"随 detail.json 落库。
```

- **副作用**：可信来源时好时坏的轮次，要等它连续 `settle_s` 都拿不到可信状态才能按时长定型；而在它能拿到可信状态的时候，本来就走终态窗口。所以只是平时多等一点。
- **夹具**：
  - `status_seq/running_then_one_500/`：running 35 分钟后一次 500，期望仍是“部分”；
  - `terminal_then_500/`：failed 之后接一次 500，期望不定型，直到终态窗口完成或连续未知满 settle_s；
  - 详情页从未配置：期望和现在一样，从记录起点开始计时。

### R-2 shelve 行的路径与清单行的路径不同时，版本比对、非 shelve 文件的取法和行对应规则都没有定义

- **位置**：§6.1 第 1a 条（[477-491](docs/enhance/vd-cosmos-loganalyzer-hld-v0.9.1.md#L477-L491)）；附录 I 的“VD 线处理 shelve 的做法”一行：“报告里 shelve 包那一行显示 shelve 所在分支的路径”。
- **问题**：这句话说明报告行的路径可以和 base 清单行的路径不同，但正文没有写不同时怎么办。
  - **行对应**：核对规则说清单行和报告行“按包键对应”，而包键含路径（[353](docs/enhance/vd-cosmos-loganalyzer-hld-v0.9.1.md#L353)）。路径不同就对不上，会报“构建输入与报告不符”，整轮停下。
  - **版本比较**：“与本轮版本（清单 CL 上该文件的版本）比较”，比的是 `#rev`，而 `#rev` 是按 depot 文件各自编号的。shelve 里的 `//…/dev_x/pkg/foo.cpp#3` 和清单路径上的 `//…/main/pkg/foo.cpp#12` 是两个文件，比出“更旧”没有意义。
  - **非 shelve 文件**：第 ① 类换算“接到本轮输入行的包根后面”。shelve 包的输入行是分支路径，于是不在 shelve 里的文件会去分支路径上按清单 CL 取，取到的是分支在那个时刻的内容，却被记成“版本确定（base 清单）”。
- **反例**：
  - 清单写 `//VD/main/apps/AT-HUB/...@14200000`；shelve 14288393 的文件在 `//VD/dev_clang/apps/AT-HUB/` 下，`foo.cpp` 基于 #3；
  - 按字面实现，会去取 `//VD/dev_clang/.../foo.cpp@14200000`，得到 #3，判“原样叠加”；
  - 实际 Cosmos 编译的应该是 main#12 合并 shelve 改动之后的结果。取错了版本，标签却是确定的。
- **说明**：19091860 实测 545 个 shelve 行都在清单里找到了 base 行，可能这一轮两者路径全部相同。但规则必须把“路径不同”当作一个明确的情形来处理。

```diff
       - **本轮 base 清单**……
+        - shelve 行与清单行的对应：按"包根路径去掉 [INT] / [FET] / [COSMOS] 标记后相等"对应；对不上时再按包名对应，并记"分支不同"。
+        - **分支相同**（shelve 文件的 depot 路径都在清单包根下）：按现行规则处理。
+        - **分支不同**：不在 shelve 里的文件一律从清单包根取（不从 shelve 分支取）；shelve 文件先把路径里的 shelve 分支包根
+          替换成清单包根，得到"目标文件"，"本轮版本"取目标文件在清单 CL 上的版本；
+          shelve 的基础版本与目标文件不是同一个 depot 文件，三方合并缺少可靠的共同祖先 → 记"跨分支 shelve，基础版本无法比对"，
+          只能诊断（以后可以按 `p4 integrated` 找共同祖先，另立规则）。
 §14 第 16 条 ⑤ 增加：统计 19091860 的 545 个 shelve 行里，报告行包根与清单行包根不同的有几个（3 个样本各自是否相同）。
```

- **副作用**：跨分支的 shelve 包只能诊断。要是侦察结果为 0 个，这条规则只是一道保护，不影响第 3a 批。
- **夹具**：
  - 假 p4 加假清单：shelve 在分支上、清单在 main 上 → 期望非 shelve 文件取自 main、shelve 文件记“跨分支”、仅诊断；
  - 同一分支的情形 → 期望结果与现行规则一致。

## 一般

### G-1 “版本确定（base 清单）”和 §14 第 14 条①仍未确认之间，标准不一致

- **位置**：[484](docs/enhance/vd-cosmos-loganalyzer-hld-v0.9.1.md#L484)、[1071](docs/enhance/vd-cosmos-loganalyzer-hld-v0.9.1.md#L1071)。
- **问题**：§14 第 14 条①“Quickbuild 对 shelve 包是否确实按 base 清单同步”还写着待确认；而 shelve 包里不在 shelve 中的文件，已经直接记成“版本确定”。同一份文档对“区间内一致”的要求是“§14 确认之前不算确定”，两边口径不同。
- **证据确实很强**：非 shelve 的 1699 行与清单完全一致。只是 shelve 包那一行，报告里给的是 SCL，没有给出实际同步用的 CL。
- **改法**：这类文件记“版本确定（base 清单；shelve 包的同步方式待 §14 第 14 条①确认）”，可以作为分析输入，但在任务包里和“已合并”一样加注“尚未确认”；等第 14 条①结清后再去掉注释。不降级为仅诊断。

### G-2 shelve 的文件动作和三方合并：有几处没有定义完

- **位置**：[490-498](docs/enhance/vd-cosmos-loganalyzer-hld-v0.9.1.md#L490-L498)。
- **add 动作**：没有基础版本，“与本轮版本比较”这一步无法执行。
  - 清单 CL 上这个路径不存在 → 应记“原样叠加”；
  - 已经存在（别人后来加了同一路径）→ 应记“合并失败（add 冲突）”。
  - 主错误在 shelve 新加的文件里，是最常见的情形之一。
- **关键字展开**：三方合并的三份输入（`print #b`、本轮版本、`@=SCL`）都会展开 `$Id$`、`$DateTime$`。在 `text+k` 文件上，两边都“改了”关键字那一行，会造成假冲突。
  - 改法：三份都用 `print -k` 取，合并后再按本轮的规则展开；或者直接记“关键字文件，合并失败”。
- **`git merge-file` 的用法要写死**：
  - 参数顺序固定为“本轮版本、基础版本、shelve 内容”；
  - 退出码 0 表示无冲突，大于 0 是冲突数，小于 0 是错误，后两种都记合并失败；
  - 建议把 `snapshot.merge_command` 从“命令字符串”改为只允许选合并工具，参数顺序由代码固定，避免配错顺序导致合并结果颠倒。
- **夹具**：
  - add 一个新文件、清单上不存在 → 原样叠加；
  - add 一个清单上已存在的路径 → 合并失败；
  - `text+k` 文件、两边都没有改正文 → 无冲突；
  - 参数顺序颠倒的配置 → 拒绝加载。

### G-3 `SHELVE_LIST` 只核对条数

- **位置**：[481](docs/enhance/vd-cosmos-loganalyzer-hld-v0.9.1.md#L481)：“`SHELVE_LIST` 的条数与报告里 shelve 行数一致”。
- **反例**：两个包的 SCL 在变量页和报告里互换，或者某个 SCL 写错，条数照样相等，核对通过。附录 I 刚更正过“按名字片段把 esplusplayer 的 14357960 当成 plusplayer 的”，这正是只比条数发现不了的那类错配。
- **改法**：按包逐一比对：报告每个 shelve 行的（包键, SCL）必须在 `SHELVE_LIST` 里，而且 SCL 相同；多出、缺少、SCL 不同的分别列出。
- **夹具**：两个 SCL 互换 → 期望写“构建输入与报告不符”。

### G-4 变量页没有纳入 §5.4 第 1 条的抓取规则；白名单里的值命中凭据检查时怎么办没写

- **位置**：§5.4 第 1 条只列了“报告首页、目录索引、详情页、失败日志”；§6.1 [478-479](docs/enhance/vd-cosmos-loganalyzer-hld-v0.9.1.md#L478-L479)；§5.4 第 3 条“页面文件按内容去重保存”。

**1. 抓取规则。** 变量页要明确适用以下规则：
- 不跟随重定向。如果被重定向到登录页，页面上会有密码框；
- 不完整就算抓取失败；
- 不进入“页面按 sha256 落盘去重”的通用路径。第 2.1 批的读取代码会把报告页存盘，变量页如果复用这条路径，“不落盘”就会被违反；
- 失败时的留证只记响应头、长度和摘要，不记正文。

**2. 凭据检查命中时的处理。** `BASE_REPOS` / `PRODUCT_REPOS` 这类仓库 URL 里常带 `user:token@`，“落盘前过凭据检查”命中之后怎么做，没有写。
- 改法：仓库 URL 去掉 userinfo 部分后再落盘，并记“已去除凭据”；`PACKAGE_LIST` 或 `SHELVE_LIST` 命中 → 停止并写待办。

**3. 身份。** 变量页没有像详情页那样核对身份，但逐行核对报告已经足以证明这是本构建的页面。这一点没问题，建议写一句说明。

**夹具**：
- 变量页返回 302 → 抓取失败，不跟随；
- 抓取后数据根目录里找不到含 `BART_PASSWD` 的文件；
- `BASE_REPOS` 含 `https://u:p@host/...` → 落盘的值不含 `u:p`。

### G-5 `confirm-terminal` 只绑定一个 `--report-digest`，而期望架构有两个

- **位置**：[697-700](docs/enhance/vd-cosmos-loganalyzer-hld-v0.9.1.md#L697-L700)。
- **问题**：一次确认现在同时用于定型、最终日志和闸门三处，但绑定的报告摘要只有一个。x86_64 的报告变了，是否让这次确认失效，没有写。
- **改法**：
  - 绑定“各期望架构的报告摘要”这个映射，回显时逐个架构列出，任一架构的报告变化即失效；
  - 补一句：提交意图写入之后，`--withdraw` 只留痕，不影响已经释放的提交。
- **夹具**：只改变 x86_64 的报告 → 期望确认失效，三处一起失效。

### G-6 `p4_unclassified` 会无限重做；“退出码与消息一致”应以录制结果为准

- **位置**：[226-235](docs/enhance/vd-cosmos-loganalyzer-hld-v0.9.1.md#L226-L235)。
- **问题一：退出码规则可能把一整类结果判成“分不清”**。p4 在 `-G` 下对错误返回什么退出码，各版本之间有差异；据我所知，有些版本在 `-G` 下出错也返回 0。如果构建机上的版本正是这样，“有错误消息却返回 0 → `p4_unclassified`”就会把所有错误都归成“分不清”，“历史输入已不存在”这一类永远到不了。结果又回到 v0.8 想消除的“每次 tick 都重做”。
- **问题二：没有重做上限**。`p4_unclassified` 按快照失败处理，每次 tick 都会重做，没有上限。
- **改法**：
  - 退出码与消息的对应关系，写成“以 §14 第 16 条②的录制结果为准，录制结果与规则不符时修改规则”；
  - 同一个包连续 N 次（默认 3 次）`p4_unclassified` → 停止对这个包重做，写待办，由人处理。
- **夹具**：录制得到“出错时返回 0”的样本 → 期望按消息分类，不判 unclassified；连续 3 次 unclassified → 不再重做。

### G-7 Clang 版本只比较版本号，没有比较发布号，也没有考虑 VD 自己的补丁

- **位置**：§6.3 匹配规则（[544](docs/enhance/vd-cosmos-loganalyzer-hld-v0.9.1.md#L544)）。
- **问题**：
  - VD 线有“编译器兜底”的专门工作（C017 提到），说明 clang 可能带 VD 自己的补丁；补丁可以新增诊断，或改变诊断分组。
  - 只比较 `22.1.8`，同一版本号下发布号的变化发现不了。
  - “用上游 LLVM 22.1.8 的源码生成”这条退路，会漏掉 VD 补丁新增的诊断。
- **改法**：
  - 比较 base repodata 里 clang 包的完整“版本-发布号”；
  - 退路改为使用 base 仓库里 clang 的源码包，而不是上游源码；
  - 核对 r15clean 根目录里 clang 的“版本-发布号”与本轮一致后才使用。

### G-8 防泄漏检查会被任务包自己的包名和构建号命中

- **位置**：§11 第 3 条（[1009](docs/enhance/vd-cosmos-loganalyzer-hld-v0.9.1.md#L1009)）。

  - 结果是 3 个 shelve 样本，乃至所有样本的检查都会 FAIL。
  - 真正的泄漏信号是：其它样本的名字，以及参照集里的修法内容。
- **改法**：
  - 对样本 X 的任务包，搜索“其它 6 个样本的全部写法”，以及“参照集里实际修法的 CL 号和修改片段的特征串”；
  - X 自己的名字和构建号只在“规则 / 模板 / SKILL.md”这几段里搜；
  - 任务包的开头和合并通知，明确归入“本包证据段”。
- **夹具**：
  - AT-HUB 的任务包只在开头出现 AT-HUB → 期望通过；
  - 模板里出现 plusplayer → 期望 FAIL；

```diff
- SHELVE_LIST 的条数与报告里 shelve 行数一致。

+ （规范化包键、depot 路径、SCL）多重集合完全一致。
+ 每个报告包必须唯一对应一条 base 行；
+ 重复键、多个候选、重复变量名均拒绝，不取第一条。
+ 去掉显示标记不得丢弃用于区分分支的 depot 路径。

+ bind-base-list 明确区分：
+ 提供 base 和 shelve 两份清单时执行完整核对；
+ 只提供 base 时，以报告记录的 SCL 作为 shelf 来源，
+ 记录“人工绑定 base、未取得原始 SHELVE_LIST”，
+ 不声称完成了变量页清单核对。
```

**副作用：**部分过去可模糊匹配的清单会转人工处理；保留多出包的现有记录策略即可。  
**夹具：**相同条数但 SCL 不同；重复包替代缺包；重复变量名；去标记后冲突；变量页完全不可用时人工绑定。

**R2｜“请求中声明的 base”仍被直接升级成“实际构建版本确定”**

**位置：**§6.1 第 1a 条，第 477、484、493 行；§14 第 14 条，第 1071 行。

**触发与后果：**正文将变量页清单版本记为“版本确定”，但 §14 仍明确待确认“Quickbuild 对 shelve 包是否确实按请求里的 base 清单同步”。这两个口径不一致。

**反例：**非 shelve 包都按 `PACKAGE_LIST` 构建，shelve 包却按另一同步规则处理。1699 条非 shelve 行完全一致、545 个 shelve 包都有 base 行，仍不能排除这种情况。当前侦察证明了请求值和覆盖关系，没有证明 shelve 包的实际同步行为。

候选修改：

```diff
- 有本轮清单时……记“版本确定（base 清单）”。
+ 有本轮清单时，先记“请求 base 已确定”。
+ 对 shelve 包，只有 §14 第 14 条①经构建实现、
+ 执行记录或对应源码版本证据确认后，
+ 才升级为“版本确定（base 清单）”。
+ 确认前不将其声称为实际编译输入；
+ 主错误文件依赖该未确认来源时，按仅诊断处理。
```

同时把“最新版本指本轮实际用的版本”改为“请求清单指定的目标版本”，直到上述确认完成。

**副作用：**可能暂时降低三个 shelve 样本的分析等级；只需结清这一同步规则，不要求逐文件重新证明。  
**夹具：**请求 base 与实际同步点一致；非 shelve 全匹配但 shelve 使用另一同步点；确认依据绑定不同构建配置时不得沿用。

**R3｜跨分支文件的 `#rev` 不能直接比较大小或相等**

**位置：**§6.1 第 1a 条，第 468、482、487—494 行；附录 I 第 1418 行。

**触发与后果：**文档已说明报告中的 shelve 路径属于 shelf 分支，而 base 清单可以指向另一分支。当前规则仍直接比较两边的版本号，可能错误判定“原样叠加”“基础超前”，或选错三方合并祖先。

**反例：**shelf 基于 `//FET/pkg/a.cc#5`，base 为 `//INT/pkg/a.cc#5`。编号相同不表示内容或历史相同；同样，FET 的 `#20` 不必比 INT 的 `#5` 更新。P4 修订号属于具体文件的历史。[Perforce 修订号说明](https://help.perforce.com/helix-core/server-apps/p4admin/current/Content/Shared/glossary.html)

候选修改：

```diff
+ 比较 #rev 前必须确认两者是同一个 depotFile。
+ 同一 depotFile 才能按 #rev 判断相同、落后或超前。
+ base 根与 shelf 根不同：
+   分别记录源文件、目标文件及其版本；
+   必须有明确的文件映射和祖先依据才能三方合并；
+   不能仅按包键或相对路径认定共同祖先。
+ 无法建立上述关系时记“跨分支来源无法核实”，仅诊断。
```

**副作用：**部分 FET/INT 跨分支情况需要额外映射；不影响同一文件历史上的自动合并。  
**夹具：**跨分支同号不同内容；跨分支编号大小相反；有明确祖先的映射；无映射；同分支正常落后合并。

**R4｜新增“非 ASCII 差异算无法核对”会放过真实源码变化**

**位置：**§6.1 第 1a 条，第 503、506 行；附录 K 第 7 项。

**触发与后果：**规则把差异仅落在非 ASCII 字节或显示标记中的情况统一记为“无法核对”，且主错误文件不降级。这包括编码明确、确实语义不同的内容，不只是显示规则不确定。

**反例：**

```cpp
// 日志中的实际源码：断言失败
static_assert(sizeof(u8"中文") == 4, "bad");

// 快照源码：断言通过
static_assert(sizeof(u8"한") == 4, "bad");
```

两者差异全部在非 ASCII 内容中，按现有规则可能保留为可编辑输入，而不是源码不一致。

候选修改：

```diff
- 差异只落在……非 ASCII 字节上 → “无法核对”。
+ 非 ASCII 本身不是“无法核对”的依据。
+ 编码和显示转换已知时，比较解码后的实际内容；
+ 有效字符不同，或可逆显示标记对应的内容不同，均记“不一致”。
+ 仅在编码/展示转换确实无法确定时记“无法核对”。
+ 主错误处的差异可能影响字面量或标识符语义时，
+ 不允许仅凭“无法核对”继续生成 edits。
```

**副作用：**部分旧编码源码需补编码依据或降为仅诊断。  
**夹具：**上述 UTF-8 字符串；不同 Unicode 标识符；同内容不同显示编码；非法字节；仅注释展示差异。

**R5｜强制合并通知会被新的防泄漏检查判 FAIL**

**位置：**§6.1 第 1a 条，第 497 行；§11 第 3 条，第 1009 行。

**触发与后果：**合并通知必须放在任务包开头，并包含构建号和包名；防泄漏规则扫描“除本包证据段和源码段之外的全部内容”，命中这些字段即 FAIL。正常自动合并因此不能通过验收。

**反例：**

```text
[shelve 已自动合并] 构建 19091860 包 AT-HUB ……
```

这是设计要求生成的通知，不是泄漏答案；按当前扫描条件仍必然命中。已用纯内存检查确认该规则冲突。

候选修改：

```diff
- 同一份通知写进任务包开头……
+ 同一份通知写进任务包开头的“工具生成证据块”，
+ 绑定合并输入摘要、生成器版本和来源事件。
+ 防泄漏检查仅豁免生成器登记的证据字段；
+ 不按任意 Markdown 标题决定豁免范围。
+ 团队规则、模板、人工注释和 AI 文本不得混入该证据块。
```

**副作用：**任务包需要结构化分段和明确来源；四处通知要求不变。  
**夹具：**正常合并通知通过；模板中泄漏同样包名被拒；伪造“证据段”标题不能绕过；人工答案不得混入工具证据。

## 一般问题

**R6｜从时长完成切换到终态窗口时，完成状态有两种相反规定**

**位置：**§5.4 第 3 条，第 390 行；§9.2 第 858 行。

**触发与后果：**此前按未知状态完成读取，随后首次取得可信终态、窗口尚未完成。§5.4 说原读取结果不作废；§9.2 则要求最新观察仍可推进，否则完成状态失效。实现无法确定此时应显示完成还是等待。

**反例：**报告 A 已按时长完成；下一次观察首次出现可信 failed，只有一次终态后观察，内容仍为 A。

候选修改，采用较简单的一致口径：

```diff
- 此前已按时长完成的读取结果，在报告内容不变时不作废。
+ 此前完成事件保留作历史记录，当前完成状态暂时失效；
+ 已下载产物不删除。
+ 终态窗口完成后，按最终日志规则验证或重新获取，
+ 再形成当前完成评估；通知不重复发送。
```

**副作用：**界面会短暂返回等待，但不要求无条件重复下载。  
**夹具：**上述切换；窗口期间重启；报告变化；有效日志重新关联；待办去重。
