# VD Cosmos 编译修复助手（LogAnalyzer 增强版）第一版 HLD v0.2（草稿）

日期：2026-10-22。设计：Claude。批准：FatTank。实施：Codex。内网验证：内网 AI（ClineSR），FatTank 在场。
仓库：LogAnalysisSkill，分支 `vd-cosmos-loganalyzer`（起点见 `docs/enhance/dev_memory/STATUS.md`）。

v0.2 相对 v0.1 的主要变化：
1. 仓库是公开的。本文件和所有提交进仓库的内容不出现内网地址、depot 路径、项目名、client 名、机器名、账号名；这些都放在构建机上的配置文件里（附录 B）。
2. 查到 Cosmos 读结果不需要登录（静态发布的构建报告），起新一轮要在需要公司 SSO 的网页表单上提交。
3. 查到另一条工作线已有一套能跑的原型（拉日志、分析、按规则改代码、本地编译验证、GCC 验证、生成 CL 和 shelve 脚本）。第一版以整理这套原型为主，不从零设计。
4. 内网有 ClineSR（VS Code 内）和 ClineSR 命令行，分析这一步可以由命令行自动调用。
5. 工具在构建机上以构建账号运行；只在自己的数据根目录下写文件。
6. Demo 目标定为周五，至少完成能力 1 和能力 2；周末由 Codex 继续。

文中【待确认】处都写了默认做法。

## 0. 定位与边界

### 0.1 本文件管什么

第一版的五项能力：

1. Cosmos 适配：定时查构建状态；构建结束后拉失败日志、解析、调用 LogAnalyzer 分析。
2. 所有失败都处理完后，生成新一轮的 shelve 清单并起新一轮 Cosmos 验证。
3. 以上做成 workflow：每一步可以单独手工调用（skill），也可以整条自动跑。
4. LogAnalyzer 接入知识库：团队定下的修法规则、以往 VD Clang 修复的案例。
5. 全量模拟：Cosmos 太慢时，按某次构建的输入在本地拉全量代码做全量编译。

### 0.2 与第二版（Compiler Agent）的关系

- 第一版每个能力都做成"输入输出是文件和 JSON、可单独调用、可重复执行"的工具。第二版 Compiler Agent 在 Multi-Agent 框架里直接把它们当工具调用。
- workflow 状态机是确定性代码；第二版换成框架的编排时，状态库和各工具不变。
- 分析这一步是可替换的"分析者"接口（§6.3），第二版由 Compiler Agent 接管。
- 第一版不做多 agent。

### 0.3 公开仓库的约束

仓库可匿名访问。因此：

- 提交进仓库的代码、文档、测试、夹具里，不得出现：内网主机名和网址、P4 depot 路径、构建项目名、P4 client 名、机器名、个人账号、构建机上的目录路径、内部产品代号。
- 这些具体值全部放在构建机上的配置文件里（附录 B 列出全部配置项），仓库里只有不含真实值的配置样例。
- 测试夹具来自内网录制的页面，入库前必须经过脱敏：主机名、depot 路径、包名、CL 号按固定映射替换成假值，保留页面结构。
- 另一条线的原型脚本只放在 Codex 本地目录 `docs/enhance/reference-local/`，用 `.git/info/exclude` 排除，不提交。
- 每批提交前跑一次敏感词检查（附录 B 末尾的词表），命中即不提交。

### 0.4 不与其他线冲突

- 同一仓库的 `clang-fix-campaign` 分支上，另一个 Session 正在做骨架收尾和 skill 拆分。本线：
  - 只新增顶层目录和 `docs/enhance/` 下的文件，不修改仓库里任何已有文件（包括根目录的 `pyproject.toml`、`.importlinter`）；
  - 新目录自带免安装入口（与现有 `run_analyzer.py` 相同的做法），import 约束写在本线自己的配置里，用 `lint-imports --config` 指定；
  - 已有能力只走命令行调用：日志分析 `run_analyzer.py analyze`、补丁上下文 `gbs_patch_suggest`。
- 构建机上另一个 Session 正在用同一棵 VD 源码树和它自己的脚本处理 Cosmos 轮次。本线在构建机上不改动它的任何目录和文件（§3）。
- 公网 Tizen 的 QuickBuild 不在本线范围。

### 0.5 角色

- Claude：设计、拆任务、写给 Codex 和内网 AI 的 prompt、审代码与证据。不写代码、不写脚本。
- Codex：实现全部代码、离线测试、内网验证脚本；推送用普通 `git push`。
- 内网 AI：只执行写死的命令并记录结果，不做判断；每次回来后再跑一次核对。
- FatTank：拍板；在人工闸门处确认；真实提交时在场。

## 1. 现状

### 1.1 一轮 Cosmos 现在怎么处理

1. FatTank（或组员）在 Cosmos 的提交页面填表起一轮。输入是：Clang build.conf（P4 上的某个版本）、LLVM base 快照、base CL 清单（APP 包用 FET 路径）、shelve 清单（约 550 行）。
2. 构建结束后发布一份静态构建报告。报告首页有"包名 | 包路径 | 结果"表，失败包带日志链接；首页同时列出本轮每个包用的 `路径@CL` 或 `路径@CL(shelve)`。
3. FatTank 把失败表贴给外网 Claude。
4. Claude 写一组命令，FatTank 在构建机终端执行：
   - 下载报告首页和每个失败包的日志，存进按轮次命名的目录（短号_构建号，例如 b123_19000123，短号是构建号末三位）；
   - 记下失败包清单（包名 | 包名-版本 | 路径@CL）和本轮输入清单；
   - 逐包提取首批错误、错误类别、依赖解析信息，并与上一轮和本地全量编译结果对比。
5. Claude 出修复。另一条线已经把修复做成了一套脚本：
   - 每个包在独立的 git 暂存树里改；
   - 先做"发现编译"，找出下一层错误；
   - 按一组确定性的修法规则改代码，例如没用到的局部 typedef 怎么处理；规则管不了的由人改；
   - 再做"确认编译"；Clang 通过后再用 GCC 验证；
   - 在专用的 P4 client 上生成 CL，最后生成一份覆盖全部 CL 的 shelve 脚本。
6. 所有失败都修好、shelve 完，FatTank 起下一轮。本地全量编译用同一批修复同步进行。

### 1.2 问题

- 每一步都要人在内外网之间搬运，3 小时时限压力大。
- 内网 AI 单独分析时考虑不全：不知道团队的修法规则，不知道同类问题以前怎么修。
- 原型脚本是一轮一轮临时生成的，每轮都要重写一份，没法复用、也没法交给别人跑。

### 1.3 第一版目标

把 1.1 的第 3～6 步做成构建机上可以复用的工具和 workflow。人只在三处介入：确认修法、确认 shelve、确认起新一轮。

## 3. 运行环境与硬约束

1. **运行位置**：内网构建机，以 VD 构建账号运行，工作在 VD 源码树所在的环境里。外网 Codex 开发机访问不到 Cosmos。
2. **只在自己的目录里写**：工具的全部输出（状态库、报告、日志副本、任务包、临时文件）都写在配置的数据根目录下，这是一个新建的专用目录。不得在 VD 源码树、其他工作目录、其他 Session 的目录里新建、修改或删除任何文件。读 VD 源码树和其他目录可以。
3. **代码送达内网**：Codex 推 GitHub，构建机 `git pull`（已确认内网能访问 GitHub）。
4. **网络**：内网服务（Cosmos、P4）的访问要绕过代理，外网访问走代理；绕过代理的主机列表放在配置里。
5. **数据不出内网**：知识库和运行数据只存在构建机上。外传只能是小块文本：工具产出的报告和证据包自带拆分命令，按行切成不超过 55KB 的块并附清单（每块大小和 sha256 前 16 位）。
6. **凭据**：
   - 读 Cosmos 构建报告不需要登录；
   - 提交新一轮要过公司 SSO，只能在浏览器里由人登录，工具不处理账号密码；
   - P4 用构建机上已有的登录票据；票据失效时工具停下提示，不自己输密码。
7. **写操作的人工闸门**：起新一轮、建 shelve CL 都要人确认。永远不做：`p4 submit`、点 Accept、删除别人的 shelve。
8. **内网 AI 的定位**：会遗忘、会编造。一切事实只由工具产生；AI 只做"填写分析模板 / 写修改规格"；它的产出必须过格式校验和规则检查；状态迁移从不依据 AI 的自述，修没修好只看编译结果。
9. **依赖**：构建机 Python 为 3.10。本线核心只用标准库；调用 LogAnalyzer 时沿用它已有的依赖（构建机上已有 PyYAML、Jinja2、tiktoken）。构建机上没有 Chromium 和 Playwright，有 Node。
10. **共享机器**：服务器上有别人的构建并发。本线的互斥只针对自己的数据根目录和自己的 GBS-ROOT。

| `vd-cosmos-core` | 公共库（无 SKILL.md） | 配置加载、状态库、数据模型、Cosmos 后端接口与实现、P4 命令封装、脱敏、页面录制、分块输出、本线的 import 约束配置、配置样例 |

| `vd-cosmos-fetch` | skill | 读报告、分类、下载失败日志、读出本轮输入清单、算阻塞下游数 |
| `vd-fix-analyze` | skill | 调用 LogAnalyzer 和知识库，生成分析任务包；调用分析者；校验结果 |
| `vd-fix-register` | skill | 登记修复；导入、导出完整 fix 清单 |

| `vd-fix-kb` | skill | 知识库：规则、案例、检索、修改检查 |

| `docs/enhance/` | 文档 | 本设计、评审记录、`dev_memory/STATUS.md` |

每个 skill 的 SKILL.md 按现有 `tizen-qb-discover/SKILL.md` 的格式写：用途、何时用 / 何时不用、输入、输出、退出码、命令示例。

### 4.3 依赖方向

- 允许：任一 skill → `vd-cosmos-core`；`vd-cosmos-workflow` → 各 skill 的公开函数。
- 禁止：skill 之间互相 import（workflow 除外）；`vd-cosmos-core` 依赖任何 skill；import 已有 skill 的内部模块。
- 写成本线自己的 import-linter 配置，每批都跑。

### 4.4 命令约定

- 入口：`python3 <skill目录>/scripts/run.py <子命令> --config <配置文件> [参数]`。
- stdout 只输出一个 JSON 对象；给人看的内容写文件。
- 退出码：0 成功；2 参数错；3 需要人处理（等确认、等分析、等登录）；4 被规则拒绝；5 后端出错（网络、页面解析失败）；6 前置条件不满足（例如报告还没发布）。
- 所有写入都在数据根目录下；同参数重复执行结果相同。
- 每个 skill 都支持 `--backend fixture --fixture-dir <目录>`，离线可跑。

### 4.5 数据根目录（构建机，路径在配置里）

```
<数据根目录>/
  config.json            运行配置（真实值；不含凭据；不进仓库）
  state/state.db         状态库（SQLite，只追加）
  rounds/<短号_构建号>/  每轮：报告首页与录制页面、结果表、失败日志、本轮输入清单、对比报告、新清单
  tasks/<轮次>/<包>/     分析任务包与填回的结果
  kb/                    知识库（§7）
  reports/               每轮报告与分块
  tmp/                   临时文件
  inbox.md               待人处理事项
```

为了和现有流程衔接，`rounds/<轮次>/` 里同时生成现有格式的失败包清单（`包名|包名-版本|路径@CL`）和本轮输入清单，现有的对比脚本可以直接读。

## 5. Cosmos 适配（能力 1）

### 5.1 已知

- Cosmos 有两个 QuickBuild 实例：
  - **构建管理实例**：访客可读；构建结束后在固定路径下发布静态构建报告；
  - **提交实例**：要过公司 SSO；起新一轮在它的一个 Wicket 表单页面上填写提交。
- 报告首页路径的规律：`<报告根>/b<构建号末三位>/<构建号>/html/Build_Report_<架构>/index.html`；失败日志在 `logs/fail/<包名-版本-发布号>/log.txt`。
- 报告首页内容：
  - 包结果表：包名、包路径（`路径@CL` 或 `路径@CL(shelve)`）、结果，失败包带日志链接；
  - 本轮全部包的输入行；
  - 汇总数字。
- 包结果至少有：成功、失败、依赖缺失未编（"nothing provides"）；还见过 expansion error、export error。
- 架构以 armv7l 为主，另有 x86_64 少量包。

### 5.2 未知（第二段侦察）

- 提交页面的字段：没填和填好时的表单结构（FatTank 提供两份页面文件）。
- 报告在构建进行中是否已经存在、怎么判断"已结束"；有没有可以列出构建的入口。
- 报告首页的完整结构（录一份脱敏样本做夹具）。

### 5.3 后端接口（与具体形态无关）

| 动作 | 输入 | 输出 |
|---|---|---|
| 查构建 | 构建号 | 状态：未发布 / 进行中 / 已结束 / 未知；结果：成功 / 失败 / 部分 / 未知；架构；本轮输入引用；原始页面引用 |
| 读包结果 | 构建号、架构 | 每个包：名称、版本、路径@CL、是否 shelve、结果（成功 / 失败 / 依赖缺失 / export 错 / expansion 错 / 跳过 / 未知）、日志 URL、缺失的依赖名 |
| 读本轮输入 | 构建号 | 输入行列表（路径、CL、是否 shelve） |
| 下载日志 | 构建号、架构、包 | 文件路径、大小、sha256 |
| 生成提交内容 | 新一轮请求（§8） | 表单每个字段要填的值、请求标记、核对清单 |
| 绑定构建号 | 请求标记、构建号 | 绑定结果（核对报告里的输入与请求是否一致） |
| 自动提交（以后） | 新一轮请求 | 请求号、是否已提交、是否"不确定" |

规则：
- "未知"永远不当成通过或结束。
- 抓取和解析分开：抓取只负责把页面原样存下来；解析是对存下来的页面做纯函数处理，测试全用夹具。
- 每次页面访问都留存，作为本轮证据。
- 绑定时比对：报告里的本轮输入必须与请求里的清单一致（逐行），不一致就停下报告，不进入"构建中"。

### 5.4 状态判断（不登录）

已知构建号时，轮询该构建的报告首页：

- 页面不存在 → "未发布"；
- 页面存在但汇总未完成 → "进行中"（判据在侦察后确定）；
- 页面存在且汇总完整 → "已结束"。

超过设定时长（默认 24 小时）仍未结束，写入 inbox 提醒。

### 5.5 失败排序：阻塞下游数

依赖缺失的包会写出缺了哪个依赖。把缺失依赖映射回提供它的包（第一版用本轮报告里能对上的包名和 spec 声明，对不上的单列"未映射"），统计每个失败包挡住了多少下游。报告按阻塞数从大到小排。

### 5.6 页面录制与脱敏（`vd-cosmos-core capture`）

- 在构建机上运行：按给定构建号录下报告首页和若干失败日志，原样存进数据根目录。
- `--sanitize` 产出一份脱敏副本：主机名、depot 路径、包名、CL 号按固定映射换成假值，映射表只留在构建机上。
- 只有脱敏副本可以外传给 Codex 做夹具。

## 6. 分析（能力 1 后半，也是知识库的接入点）

### 6.1 每个失败包的处理

1. **源码定位**：从本轮输入取该包的路径@CL 和该包的 shelve。源码树里对应版本一致就直接读；不一致就用 `p4 print` 取到任务目录下。Demo 可以不带源码，LogAnalyzer 退化为只看日志。
2. **跑 LogAnalyzer**：得到 evidence 文件。
3. **跑补丁上下文**（`gbs_patch_suggest --evidence`）：得到 `context.md`。
4. **查知识库**（§7）：得到 `kb_context.md`。
5. **生成分析任务包** `task.md`：上面三份内容，加一个填空式结果模板。模板字段：
   - 根因类别；是否本组负责；
   - 修法类型：改代码 / spec 里加只对 Clang 生效的选项 / 修 base / 只是本地环境问题 / 需 owner 处理 / 依赖未编（不是本包问题）；
   - 修改规格 edit_spec 的路径；
   - 需要 owner 确认的事项（我们的做法 + owner 可选的最终形态）；
   - 依据了哪些知识库条目。
6. **结果校验**：分析者写回 `result.json`，工具检查格式和枚举值、引用的知识库条目是否存在、edit_spec 是否通过现有格式守卫、修改检查（§7.5）。不通过就打回：状态保持"待分析"，原因写进任务目录。

### 6.2 已有能力的复用

LogAnalyzer 和补丁上下文都通过子进程调用，命令和输出文件照它们 SKILL.md 里写的稳定入口；产出原样保存，本线只读。

### 6.3 分析者接口

| 方式 | 说明 | 第一版 |
|---|---|---|
| ClineSR 命令行 | workflow 以任务包为输入调用 ClineSR 命令行，要求它只写 `result.json` | 默认（侦察确认命令行用法后启用） |
| ClineSR 手工 | 任务包写入 inbox，ClineSR 在 VS Code 里按 SKILL.md 处理并写回 | 命令行不可用时 |
| 无 | 只生成任务包 | 调试 |

三种方式产出同一种 `result.json`，后面的校验和流程完全相同。调用命令行时：只给它任务目录的写权限约定（prompt 写明只能写 `result.json`），超时、退出码、产出文件都由工具检查；它写到任务目录以外的任何东西都不被读取。

## 7. 知识库（能力 4）

### 7.1 目的

给能力有限的内网 AI 补上它自己想不到的三样东西：团队定下的修法规则；同类错误以前怎么修、最后采用了哪个方案；这个包以前出过什么问题。

### 7.2 四类条目

- **规则**：人工审定。字段：编号、标题、适用范围（错误类别、警告名、包类型、路径标签）、正文、正例、反例、来源（哪天的裁决）、状态（生效 / 废止）。种子见附录 A（脱敏版；带具体包名的完整版只放在构建机上）。
- **可执行修法**：原型里那组确定性的改代码规则（例如没用到的局部 typedef、未使用变量的处理），整理成带名字、带适用诊断、带反向测试的修法函数。每个修法函数对应一条规则。
- **案例**：一次具体修复。字段：包名、路径；错误签名（原文和归一化后）、诊断标志、根因类别；修法类型、修复摘要、shelve CL 号和改动文件；候选方案（改代码 / 加选项 / 删参数）、需 owner 确认的事项；来源（本组 / 组员 / 总部）；首次出现的轮次；状态。
- **包备注**：这个包的已知事实（本地需要签名服务器、APP 包要走 FET 路径、只有 x86_64 失败等）。

### 7.3 案例状态（机器判定）

| 状态 | 判定 |
|---|---|
| 新建 | 登记时 |
| 本地已验证 | 有按 Cosmos 条件的本地验证证据（Clang 和 GCC） |
| Cosmos 已通过 | 该 CL 出现在某轮输入里，且该包在那一轮成功 |
| 最终采用 | 进入最终清单或 owner 已合入（人工标记） |
| 失效 | 同包同错误在带着该 CL 的轮次里仍然失败 |

只有"Cosmos 已通过"及以上的案例才作为可参照的先例；之前的只作为"进行中"提示。

### 7.4 检索（确定性阶梯，不用向量库）

1. 同包、归一化签名相同；
2. 诊断标志相同，或链接错误类别相同；
3. 根因类别相同。

另外附上按标签匹配到的规则、可执行修法和本包备注。每层限条数，总量控制在约 8KB。命中层级写进任务包；只是"同类别"命中的案例只作参考。归一化复用 LogAnalyzer 已有的错误签名归一化。

### 7.5 修改检查（确定性，触犯即打回）

- 删除 GCC 专用选项或功能，却没有加编译器条件；
- 改了 2027 以外年份目录的代码；
- spec 里加 `-Wno-error` 类选项却没有包在 `%if "%{?_toolchain}" == "clang"` 里；
- 用了 `%{toolchain_is …}`；
- 引入 `CCC_OVERRIDE_OPTIONS`，或全局加 `--as-needed`；
- 直接删除未使用的变量、函数、成员（要求注释掉并加说明）；
- 修改 build.conf；
- 对标记为"疑似真 bug"的诊断（如 sizeof 指针当长度、某分支未初始化）用只对 Clang 生效的选项规避，而不是改代码。

每条检查都有反向测试：植入对应的违规改动，确认会被拦下。

### 7.6 存储

数据根目录下的 `kb/`：SQLite 存条目，可导出 JSONL；diff 原文另存文件，库里只存路径和 sha256。写操作加文件锁、原子改名；规则修改留痕。

### 7.7 来源

1. 每轮的 fix 清单和其中的 shelve CL（`p4 describe -S` 取说明和 diff，含总部和组员的）；
2. 每轮的失败日志：生成错误签名；
3. Clang 修复评估总表（FatTank 周五整理出总的版本）；
4. 规则种子（附录 A）和原型里的修法规则；
5. 可选：构建机上同事已有的 clang 修复知识库（公网 Tizen Gerrit 来源，约 510 条），只作同类别参考，不作先例。

导入后按 §7.3 用历史轮次结果自动定状态。

## 8. 起新一轮（能力 2）

### 8.1 闸门：全部满足才生成新一轮请求

1. 最近一轮已结束，结果已拉取。
2. 该轮每个本组负责的失败包都已"本轮处理完"，即处于以下之一：已登记修复且有本地验证证据；需 owner 处理；本地环境问题；依赖未编（不是失败）；人工决定本轮跳过（必须写原因）。
3. 新清单通过 §8.3 的检查。

### 8.2 生成新清单

- 上一轮输入 + 本轮新登记的修复（替换或新增）= 新清单。清单带版本号，相邻版本可 diff。
- 同时输出一份完整、可直接复制粘贴的 fix 清单，包括原样采用的总部和组员 CL。
- 清单格式与现有提交时贴的格式一致（侦察后确定）。

### 8.3 清单检查（确定性）

- 已经有 base 的包沿用原 base，不得改；没有 base 的包用最新，除非显式覆盖并写明原因；
- APP 包必须是 FET 路径；
- x86_64 包的 shelve 不进清单，标记"需 owner 提交"；
- 同一个包有多个 shelve 时以本组的为准，他人的 CL 号记为对照；
- 同一个 CL 不重复；格式合法。

### 8.4 提交（Demo：生成内容 + 人工提交 + 绑定）

1. 工具按提交页面的字段，生成每个字段要填的值，外加一个唯一的请求标记（写进构建说明一类的字段），以及核对清单（清单 diff、build.conf 版本、base 快照）。
2. 人在浏览器里登录提交页面，按内容填写、提交，得到构建号。
3. `bind --request <标记> --build-id <构建号>`：工具读该构建的报告（发布后），逐行比对本轮输入与请求清单；一致才进入"构建中"，不一致就停下报告。
4. 报告发布前绑定的，先记为"待核对"，报告发布后自动核对。

### 8.5 自动提交（周末验证可行性，以后实施）

提交页面和另一条线已经自动化过的 QuickBuild 表单是同一种产品，那边的浏览器驱动方式可以复用：工具弹出浏览器窗口，人只在窗口里登录 SSO，工具填表提交并按请求标记认领构建号。前提是构建机上能装 Chromium（侦察会测下载是否可行）。

## 9. Workflow（能力 3）

### 9.1 两种用法

- **手工**：每个 skill 单独调用（ClineSR 读 SKILL.md 后调用，或人在终端调用）。
- **自动**：`vd-cosmos-workflow loop`，内部反复执行 `tick`。

### 9.2 tick

每次 tick：读状态库 → 只做"下一步"里的一小步 → 写状态库 → 返回。重复执行结果不变；崩溃或重启后从状态库接着走。

### 9.3 状态机

轮次：

```
已绑定（待核对）→ 构建中 → 已结束 → 结果已拉取 → 分析中 → 等待修复
        → 待起新一轮（生成提交内容，等人提交）→ 已提交（等绑定）→ 已绑定 …
构建全部成功 → 完成（出最终报告）
```

失败项：

```
新发现 → 日志已下载 → 任务包已生成 → 已分析（结果通过校验）→ 已登记修复
      →（周末起：本地已验证 → 已建 shelve）→ 已进新清单
旁支：需 owner / 本地环境问题 / 依赖未编 / 本轮跳过
```

状态库只追加：每次迁移是一条事件，当前状态由事件推出。

### 9.4 人工介入点

1. 确认修法（分析结果）；
2. 确认建 shelve（周末起）；
3. 在网页上提交新一轮并绑定构建号。

待办写进 `inbox.md`，loop 在终端上提示。

### 9.5 loop 进程

- 长驻运行（tmux 或 nohup）；读报告不需要会话。
- 服务器重启后重新启动 loop 即可续跑。
- 单实例锁：同一数据根目录只允许一个 loop。

### 9.6 报告

每轮一份 Markdown，可直接贴 Confluence：成功 / 失败 / 依赖未编数量与上一轮对比；失败包表（结果类别、阻塞下游数、分析状态、修复 CL、owner 待决项）；新清单与上一轮的 diff。外传时用自带的拆分命令。

## 10. 修复落地（周末起）与全量模拟（下周起）

### 10.1 修复落地 `vd-fix-apply`

把原型的修复链整理成可复用的 skill，行为以原型为准：

1. 每个包在数据根目录下的独立暂存树里改（git 管理，便于回退和出 diff）；
2. 发现编译 → 按修法规则改 → 人或分析者补改 → 确认编译；轮数有上限，上限可配置；
3. Clang 通过后做 GCC 验证；
4. 本地编译条件必须与 Cosmos 一致（同一 build.conf 版本、同一 base 快照、同一清单）；
5. 在专用 P4 client 上生成 CL，说明里写明改动原因和 owner 待决项；
6. 生成 shelve 脚本，人确认后执行；
7. 结果自动登记为修复（§8）并追加为知识库案例（§7）。

原型里只为某一轮写死的部分（包名、目录名、轮次号）全部改成参数。

### 10.2 全量模拟 `vd-full-build-sim`

1. 输入一个 Cosmos 构建号；工具从报告读出本轮输入。
2. 复用已经实战过的全量编译脚本（manifest 叠加、依赖图、按依赖顺序编译的调度器），原样搬入、外面包一层。
3. 每次模拟一个独立任务目录，只共用源码树；支持增量和全新两种模式。
4. 结果按 §5.3 的同一接口输出，workflow 可以把一次本地全量当成"一轮"处理。

## 13. 风险

| 风险 | 应对 |
|---|---|
| 周五时间紧 | Demo 只含能力 1、2、3 的主路径；提交走"生成内容 + 人工提交 + 绑定" |
